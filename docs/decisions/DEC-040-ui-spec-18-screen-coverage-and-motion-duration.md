## 1. 背景

老板 2026-11-01 反馈「现在 ui 感觉还是有点粗糙，能不能商业化页面 ui 点，精致点」。QUOT-306 把它量成三条根因，第一条就是规范失覆盖：

- `docs/UI-SPEC.md` v1.0 的标题即「看板信息架构与视觉规范（**四屏**）」，§0 覆盖只写「复盘 / 盯盘 / 验证 / 日志」，§11 的 10 条验收也只针对这四屏。
- 产品在 `270caf8` 上实际有 **18 屏**（`frontend/src/screens/`：8 张根屏 + `industry/` 2 + `radar/` 4 + `research/` 2 + `signals/` 1 + `limitup/` 1）。后 14 屏没有任何视觉基线，§12.3 的「按 §11 逐条走查」在物理上走不到它们。
- 更糟的是 v1.0 的若干**全局**条款（§2 外壳与断点、§7 token 表、§8 数字口径、§6 组件清单）已经与代码分叉：它描述的圆角五档、字号含 13px、标题 22px、`kit/Badge.tsx` 等 11 个组件文件、`<1024` 顶部横向导航，在 `270caf8` 上都不存在。这本身就是"规范说 A、代码是 B"，也是粗糙感被合理化的入口——每屏都可以声称自己合规。

结论：不补齐规范，阶段二/三的"精修"就没有可判过/不过的依据。本决策只做两件事：**把覆盖补齐**，并**当场裁掉一个已知的硬冲突**（过渡时长），不留给验收人去发现。

## 2. 决定

### 2.1 UI-SPEC 覆盖范围扩至 18 屏，验收条目逐屏化

1. `docs/UI-SPEC.md` 升 **v1.1**，标题改「看板信息架构与视觉规范（18 屏）」，变更记录加一行。
2. §0 出「18 屏逐屏表」：路由（以 `App.tsx:54-76` 为准）+ 侧栏入口（以 `Layout.tsx:64-119` 为准）+ 契约码。
   **纠正派单前提**：不存在 `/radar/*` 路由族，雷达家族实际是 `/news` `/calendar` `/pool` `/positions`；本决策一律按代码写。
3. §3 从「四屏信息架构」改为「逐屏信息架构」：§3.1–§3.4 保留原四屏（含全部原有状态矩阵，仅按代码校正断点与行号），§3.5–§3.18 为 14 张新屏各补一节，统一五要素：**入口 / 工具栏 / 主区结构 / 六态（含区块四态）/ 降级与溯源徽标**，每条给 `文件:行号`。
4. §11 由「四屏清单 10 条」改为「**§11.0 全局条目（每屏都过）+ §11.1–§11.18 逐屏条目**」。写法约束：每条必须是可判真假的可观察事实（元素、token、文案逐字、`?state=`/`?demo=1` 下的表现），**禁止**"更精致 / 更有质感 / 商业化一点"类措辞进入验收条目。
5. §6 组件清单按实际文件与契约码重写（`ui/*` + `PageShell` + `charts/*` + `research/*`），并登记**缺口**（§6.3）：C-09 缺 `summaryRow`/`expandable`、无 `SourceBadges`、`Button` 无 link 变体、1024 档无断点名。
6. §2 / §7 / §8 中与代码冲突的原条款**逐条裁定**：要么改规范并写理由（§12.4 A–N），要么进整改清单（§12.5 R-01…R-26）。不允许保留"规范说 A 代码是 B"。

### 2.2 过渡时长：交互过渡一律 `--ldst-duration-fast`（120ms），180ms 登记为受限例外

**冲突**：QUOT-306 验收要求「hover/press/展开的过渡在 24–160ms」，而 `tokens.css:132` 的 `--ldst-duration-base` 是 **180ms**。若两条同时生效，任何一处用到 `duration-base` 的过渡都必然不过验收，但最终会表现为"实现与规范互相打脸"或"验收人临场裁定"，两者都是我们要消除的。

**实测的三条事实**（决定了本裁定的形态，不是拍脑袋）：

| 事实 | 依据 |
|---|---|
| 180ms 的**声称用途**（抽屉滑入、Toast 进出）在代码里根本没有实现——`ui/Overlay.tsx` 与 `ui/Feedback.tsx` 内零 `transition` | 全仓 `duration-base` 命中仅 4 处 |
| 180ms 的**实际用途**是两个进度条宽度填充：`SettingsScreen.tsx:340`、`research/ResearchReportScreen.tsx:79` | 同上 |
| 另有一处**死引用**：骨架扫光先引用 `--ldst-duration-base` 再在下一行被 `1200ms` 覆盖（`styles/index.css:80-81`） | 同上 |
| 其余交互过渡（按钮 / 输入 / 分段 / 表格行 / Tabs / 侧栏 / 时间线 / 段轨）已**全部**是 `duration-fast` = 120ms | `ui/Button.tsx:17,101` 等 15 处 |

**裁定**：

1. **交互过渡只用一档**：hover / focus / press / 展开折叠 / 选中态 / 路由内状态切换 = `--ldst-duration-fast`（**120ms**）+ `--ldst-ease`。它天然落在 24–160ms 内，QUOT-306 的过渡验收**只测这一档**。
2. **`--ldst-duration-base`（180ms）不删除、不改值，登记为明确例外**，作用域收窄为两类非交互过渡：
   - **浮层进出**：C-15 抽屉滑入滑出、C-14 Toast 进出；
   - **连续值填充**：进度条 / 分位条的宽度补间。
   这两类都不属于"用户按下去要立刻得到反馈"的交互过渡，不在 24–160ms 预算内衡量。已在 `UI-SPEC §7.5` 以表格形式登记，验收人按表判定，不再现场裁量。
3. **不新增第三个时长刻度**。理由：新增 160ms 档会与既有 120/180 形成"三档过渡"，实际选择成本大于收益；且现网已 100% 落在 120ms，加档不解决任何现存问题。若将来确有第三种需求，走 §7.4 的加 token 流程（改 `tokens.json` → 重新生成 → 在 §7.5 登记），而不是在业务代码里写 `duration-[150ms]`。
4. **环境类动画显式排除在过渡预算之外**：骨架扫光 1200ms、`StatusDot` 呼吸 1600ms、Toast 自动消失 4000ms 属"循环/提示"类，不参与 24–160ms 判定；但它们在 `prefers-reduced-motion` 下必须归零或转静态（`tokens.css:193-198`、`index.css:93-105,126`）。
5. **两个待整改项随本裁定一并登记**：R-19（抽屉/Toast 要么实现 180ms 进出，要么把 `tokens.json` 的 usage 注释改准，二者择一，不许留着空承诺）；扫光那条死引用应删掉对 `--ldst-duration-base` 的引用（属 R-19 同一动作）。
6. `prefers-reduced-motion: reduce` 仍是硬要求，两档时长同时归 0，QUOT-306 验收第 4 条"允许 prefers-reduced-motion 关闭"由此有明确落点。

### 2.3 最低支持视口定为 1024，撤销两条从未实现的窄屏条款

v1.0 §2 写着「`<1024` 侧栏折叠为顶部横向导航」「`<720` 表格转卡片列表」。`270caf8` 上 `Layout.tsx:194` 只有 `w-sidebar`(232) / `rail:w-sidebar-rail`(56) 两档，`rail` 的定义是 `max-width: 1279px`，**没有任何 `<1024` 或 `<720` 分支**；`tokens.json` 里 `layout.breakpointMin: 1024px` 也只是个"保底宽度"数值，连 Tailwind 档名都没注册（→ R-04）。

裁定：**最低支持视口 = 1024×768**（`--ldst-bp-min`），两条不可达的窄屏条款从规范中删除而非"待实现"。理由：保留一条永远无法通过的验收项，会让 §11 整份清单失去可信度；而"支持到 720"是产品决策，不在本次视觉精修范围内，需要时另开决策。

同时把断点词汇收敛为**只有两档命名变体**：`rail:`（≤1279）与 `desk:`（≥1280）；`min-[1024px]` / `min-[1100px]` / `min-[640px]` 这类临时断点列为违规（10 处，R-04）。

### 2.4 其余"改规范"的裁定（完整理由见 `UI-SPEC §12.4`）

- 标题层级以 token 为准：页面 28/600、页内分区 20/600、卡片标题 16/600、正文 14、说明 12、主指标 36；v1.0 的 22px 作废（本文自己规定 CSS 为唯一真源，冲突时文档回改）。
- 圆角由 v1.0 的五档收敛为三档（`8 / 4 / 999`），与 `tokens.json` v2 一致；字号去掉不存在的 13px，行高去掉 1.25。
- §7.4「不用 Tailwind 与 token 混用」改为「语义类即 token 引用；禁的是 Tailwind 默认档泄漏与 `[...]` 任意值」——`tailwind.config.ts` 的 `theme.extend` 全量由 `tokens.json` 生成，语义类与令牌一一对应，原禁令表达的是正确的担忧但选错了对象。
- §4.4「迁移丢弃」由 danger 改 warn，与实现一致（丢的是历史草稿、不阻断当前输入；danger 保留给"本轮从空态启动"）。
- §2 内容宽度分层：`main` = `--ldst-table-max` 1296，阅读型正文再收 `--ldst-content-max` 1080。

## 3. 边界与不做

- 本决策**只改文档**（`docs/UI-SPEC.md` + 本文件），不动 `frontend/src/` 任何代码；整改项以 R-01…R-26 登记，交给 QUOT-306 阶段二/三执行。
- 不新增依赖、不引 CDN / webfont / 动画库（DEC-006 离线回环）。精致度靠既有 `lucide-react` + token 体系。
- 不改 `Layout.tsx` 的 `NAV_SECTIONS` 分组结构（QUOT-300 / QUOT-304 正在改同一文件）。
- 不碰 disk-warden 与 QUOT-305 冻结的 uitour 巡检工具。
- `docs/multica-handover/` 在本仓不存在（该目录属于 disk-warden 的接手材料），本次无只读覆盖风险；已按 §12.7 的口径引用 QUOT-307 / QUOT-309 的产出替代。

## 4. 后果

- **正面**：18 屏第一次有了同源基线；阶段二/三的每条改动都能落到"哪一屏、哪一条、过还是不过"；§12.6 把走查从"人肉抽查四屏"变成逐屏清单 + 可 grep 的自动化五类判定。
- **代价**：一次性暴露 26 项整改（其中 P0 级 2 项：R-18 演示数据无水印、R-12 色序反转），阶段二的工作量比原估更大；`docs/tasks/` 受 `.gitignore:48`（DEC-0026）排除，所以规范与决策必须落在 `docs/` 与 `docs/decisions/`，不能沉在任务目录里。
- **风险**：§11 条目变多后，若无 §12.6 的 PR 勾选机制，逐屏清单会退化成没人读的死文档。这是流程风险而非技术风险，已把"缺清单的 PR 视为未过走查"写进 §12.6。
